## Design decisions

### Module name: `protocol.py`, not `wire.py`

Restore the original module name. The `wire.py` name was introduced by the Protobuf migration to avoid a name collision with the generated stubs. With no generated stubs, `protocol.py` is the simpler, already-documented name. Import alias `from byoa_plugin import protocol as proto` works at all existing call sites (adapter.py, hooks.py, connections.py, server.py, debug_client.py, fake_client.py).

### Restore faithfully, then adapt

Take the legacy `protocol.py` from git 8437113^ verbatim, then make the minimal adaptations:
- Keep all constructor signatures identical (they already match current call sites).
- Keep `parse_client`, `STREAMING_CURSOR`, exception classes.
- The `caps` field in `hello_ok` was already optional in the legacy protocol — the current server's caps list `["text", "voice", "tool-events", "sessions", "streaming"]` fits the signature without change.
- Drop the `protocol_gen.py` import comment at the top (it referenced the deleted codegen script). Replace with a note that the TS side is hand-maintained in sync.

### Raw binary PCM stays raw binary

The Protobuf migration wrapped PCM in `AudioData` frames to make every WS message self-describing. Raw binary was simpler and worked: the server already has a `capturing` flag that gates the binary path. A stray binary frame outside capture is harmless (logged and dropped). The `AudioData` wrapping added a serialization round-trip per ~20ms chunk with no benefit — the server immediately unpacked it anyway. Restore raw binary.

### Text vs Binary WS frame dispatch

With JSON, the server's WS dispatch changes:

| Message kind | Frame type | Dispatch |
|---|---|---|
| JSON text frames | `WSMsgType.TEXT` | `parse_client(data)` → `t` discriminator |
| Raw PCM audio | `WSMsgType.BINARY` | Append to `audio_buf` if `capturing` |
| Anything else | `WSMsgType.ERROR` / etc. | Log and continue/break |

The hello handshake arrives as TEXT (a JSON `{"t":"hello",...}` frame), not BINARY. The current server expects `WSMsgType.BINARY` for the first frame — this changes to `WSMsgType.TEXT`.

### connections.py send_frame signature

Currently: `async def send_frame(self, chat_id: str, frame: bytes) -> bool` calling `ws.send_bytes(frame)`.

Changed to: `async def send_frame(self, chat_id: str, frame: str) -> bool` calling `ws.send_str(frame)`.

PCM audio is never sent through `send_frame` — the server sends it directly in the audio capture path (which doesn't exist for outbound PCM). This keeps `send_frame` single-purpose for JSON control frames.

### TypeScript: hand-maintained protocol.ts, no codegen

The legacy `protocol.ts` was auto-generated by `protocol_gen.py` from Python dict literals. That codegen script is already gone (it was deleted as part of the Protobuf migration — see OQ-2), so we hand-maintain `protocol.ts`. The JSON frame types are simple enough that drift is caught by the test suite (every constructor test round-trips) and the types are stable (frame families haven't changed in months).

### Voice confirmation: no wire changes

The voice confirmation flow (commit bb83976) added client-side logic in `main.ts`: on `transcript` receipt, display the transcript with confirm/retry choices, then send a `text` frame on confirm. This uses existing wire frames (`transcript` inbound, `text` outbound) — zero protobuf-specific fields. The revert preserves this flow unchanged.

### Version-skew behavior

Old protobuf app → new JSON server:
1. App sends binary `Frame` (Protobuf-serialized hello).
2. Server's hello handshake expects a TEXT frame; it receives BINARY.
3. Server closes the connection immediately with WS code 1002 "expected text frame" and logs `auth_failed` with `reason="non_text_first_frame"`. There is no hello timeout — the handshake is a bare `ws.receive()` with no `wait_for`, so a stale protobuf app gets a prompt close, never a silent zombie connection that waits to time out.

New JSON app → old protobuf server (hypothetical, since both sides deploy together):
1. App sends TEXT `{"t":"hello",...}`.
2. Server expects BINARY Protobuf `Frame` → `parse_frame` fails → raises `FrameParseError`.
3. Server sends error frame + close code 1002 "expected binary frame".

In practice this is a non-issue: both sides always upgrade together (one PR, one sideload).

## Wire format: complete frame catalog

Every frame is a JSON object with a `"t"` discriminator field. All other fields are optional unless noted.

### Client → Server (inbound)

| `t` | Fields | Notes |
|---|---|---|
| `"hello"` | `token: str` (required), `device: str` (default `"g2"`) | First frame; auth handshake |
| `"text"` | `text: str` (required) | User message content |
| `"audio.start"` | (none) | Begin PCM capture |
| `"audio.stop"` | (none) | End PCM capture, trigger ASR |
| `"sessions.list"` | (none) | Request session list |
| `"sessions.switch"` | `id: str` (required) | Session id or `"+1"`/`"-1"` |
| `"sessions.new"` | (none) | Create new session |
| `"stop"` | (none) | Interrupt current turn |

Binary WS frames between `audio.start` and `audio.stop` carry raw PCM16 LE 16kHz mono audio bytes — NOT JSON.

### Server → Client (outbound)

| `t` | Fields | Notes |
|---|---|---|
| `"hello.ok"` | `active?: str`, `caps?: str[]` | Auth success; caps list for feature negotiation |
| `"assistant.delta"` | `text: str` (required) | Incremental streaming text; client appends |
| `"assistant"` | `text: str` (required) | Full replacement text (divergence or first message) |
| `"tool.start"` | `name: str` (required), `label?: str`, `emoji?: str` | Tool invocation began |
| `"tool.end"` | `name: str` (required), `ok: bool` (default `true`) | Tool invocation completed |
| `"turn.done"` | (none) | Agent turn complete; clear streaming state |
| `"sessions"` | `items: [{id: str, name?: str}]` (required), `active?: str` | Session list |
| `"active"` | `id: str` (required), `name?: str` | Active session changed |
| `"history"` | `id: str` (required), `items: [{role: str, content: str}]` (required), `ok: bool` | Session history |
| `"transcript"` | `text: str` (required) | ASR result; empty string = silence |
| `"error"` | `msg: str` (required) | Error message for display |

### Notable constants

- `STREAMING_CURSOR = " ▉"`: Appended by Hermes Gateway to in-progress accumulated text. Stripped by `StreamState.delta_for()` before diffing.
- PCM format: 16-bit signed integer PCM, little-endian, 16kHz sample rate, mono, no header.

## Open questions

None at spec time — all frame families are preserved from the legacy protocol, and the post-migration features (voice confirmation) use existing frame types. The `caps` list sent in `hello.ok` is a server-side concern; the JSON schema supports any string array.

### OQ-1: Should `protocol.py` keep `INBOUND_TYPES`/`OUTBOUND_TYPES` tuples?

These were used by `protocol_gen.py` to auto-generate `protocol.ts`. Without codegen, they are documentation only. Decision: KEEP — they serve as a single-source enumeration of valid `t` values, useful for validation and testing. If they rot, a test catches it.

### OQ-2: Should `protocol.ts` be hand-maintained or regenerated?

The `protocol_gen.py` codegen script was deleted as part of the Protobuf migration. Options: (a) restore it, (b) hand-maintain `protocol.ts`, (c) add a TypeScript-side codegen from the Python constants. Decision: (b) hand-maintain — the protocol is stable (no frame type added since June 2026), and the test suites on both sides lock the format. A codegen script is infrastructure that needs its own CI gate; hand-maintenance is simpler for a stable schema.

## Known limitations

- **No schema validation**: `parse_client` only checks `t` presence, not shape correctness per frame type. A frame with `{"t":"text"}` and no `text` field will parse successfully but produce a runtime `KeyError`. This is the same limitation the legacy protocol had; the tests cover every constructor's exact shape and the callers validate fields at point of use. Full JSON Schema validation was considered but rejected as over-engineering for a wire format with two implementations that deploy together.
- **No version negotiation**: `hello.ok` `caps` is a feature list, not a protocol version. If a future change adds mandatory fields, both sides must upgrade together. This is acceptable for a single-user device with no third-party clients.

## Rollout note

Deploying this revert is a coordinated two-sided upgrade — the plugin and the glasses-app must land together (there is no wire-version negotiation).

1. **Plugin (gateway host, landing lane owns):** re-sync `/opt/data/plugins/even-g2` with the reverted tree, `plugins enable`, then a **delayed gateway restart** so the running process picks up the new `protocol.py` / `server.py`. The BYOA HTTPS endpoint (`POST /v1/chat/completions`) is unchanged and needs no separate action.
2. **Glasses-app (manual, Doni owns):** rebuild with `npm run build` and re-sideload the resulting `.ehpk` to the phone via the Even Hub CLI. Until the app is re-sideloaded it will keep speaking protobuf binary and the new server will close its first (BINARY) frame with code 1002 `expected text frame`.

Because neither side is in production today (plugin disabled, app sideloaded per-device), there is no mixed-version window in practice. Rollback is a simultaneous revert of both sides.
